# 系统架构分析：是否基于飞书多维表格

## 当前系统架构

### 技术栈
- **前端**: React + Vite
- **后端**: FastAPI + SQLite
- **部署**: Docker on Hugging Face Spaces

## 当前系统的数据流

### 1. 工时数据流

```
Excel文件 (Timesheet Report)
    ↓
后端解析 (parser.py)
    ↓
数据验证和转换
    ↓
SQLite数据库存储
    ↓
前端查询和展示
    ↓
导出为Excel或JSON
```

### 2. 数据来源

**当前数据来源**:
- Excel文件上传（手动上传）
- 文件名: `Timesheet Report-YYYYMMDDHHMMSS.xlsx`
- 解析字段: 员工、部门、工号、项目名称、工时、审批状态等

**不是飞书多维表格**:
- 系统不直接连接飞书API
- 不使用飞书多维表格作为数据源
- 数据通过Excel文件导入

## 飞书新需求对系统架构的影响

### 需求分析

用户提出的新需求包括：
1. 员工在飞书中自行填写工时信息
2. 支持部门管理
3. 工时提交后需要审批流程
4. 每周一次的定期提报（周期性同步）
5. 处理假期和工作日调整
6. 最终自动输出并链接到网站中

### 架构选择

**选项1: 基于飞书多维表格**
```
飞书多维表格 (员工填报)
    ↓
飞书API (获取数据)
    ↓
后端处理和审批
    ↓
SQLite存储
    ↓
网站展示
```

**优点**:
- 员工直接在飞书中填报，用户体验好
- 飞书原生支持权限管理
- 飞书支持工作流和审批

**缺点**:
- 需要开发飞书API集成
- 需要处理飞书API的限制和延迟
- 需要维护飞书和本地数据库的同步

**选项2: 重新设计独立系统**
```
独立工时管理系统 (Web表单)
    ↓
系统内部审批流程
    ↓
SQLite存储
    ↓
网站展示
    ↓
飞书通知 (可选)
```

**优点**:
- 完全独立，不依赖飞书API
- 可以完全自定义审批流程
- 性能和稳定性更好

**缺点**:
- 需要重新开发工时填报界面
- 需要自己实现权限管理
- 用户需要学习新系统

## 建议的架构方案

### 混合方案（推荐）

```
┌─────────────────────────────────────────────────────────────┐
│                    飞书工作台                                 │
│  - 工时填报表单 (飞书多维表格或表单)                          │
│  - 审批流程 (飞书工作流)                                      │
│  - 通知提醒 (飞书消息)                                        │
└────────────────────────┬────────────────────────────────────┘
                         │ 飞书API
┌────────────────────────▼────────────────────────────────────┐
│              后端 (FastAPI)                                  │
│  - 飞书API集成模块                                           │
│  - 数据同步模块                                              │
│  - 审批流程管理                                              │
│  - 定期同步任务                                              │
└────────────────────────┬────────────────────────────────────┘
                         │ SQL
┌────────────────────────▼────────────────────────────────────┐
│              数据库 (SQLite)                                 │
│  - time_entries (工时记录)                                   │
│  - approval_records (审批记录)                               │
│  - project_config (项目配置)                                 │
│  - standard_hours (标准工时)                                 │
└────────────────────────┬────────────────────────────────────┘
                         │ REST API
┌────────────────────────▼────────────────────────────────────┐
│              网站 (React)                                    │
│  - 工时统计仪表板                                             │
│  - 项目进度监控                                               │
│  - 数据导出                                                  │
│  - 人月占比分析                                               │
└─────────────────────────────────────────────────────────────┘
```

### 架构特点

1. **飞书作为前端**
   - 员工在飞书中填报工时
   - 飞书处理审批流程
   - 飞书发送通知提醒

2. **后端作为中间层**
   - 集成飞书API
   - 同步数据到本地数据库
   - 处理复杂的业务逻辑

3. **网站作为展示层**
   - 展示工时统计和分析
   - 提供数据导出功能
   - 支持多维度查询

## 需求文档的调整

### 当前需求文档的假设

需求文档中假设：
- 系统与飞书集成
- 员工在飞书中填报工时
- 系统支持飞书API调用
- 系统支持飞书消息通知

### 需要澄清的问题

1. **飞书集成的范围**
   - 是否使用飞书多维表格作为工时填报界面？
   - 是否使用飞书工作流作为审批流程？
   - 是否使用飞书消息作为通知方式？

2. **数据同步的方式**
   - 是否实时同步？
   - 是否定期同步？
   - 同步频率是多少？

3. **系统的独立性**
   - 是否需要在飞书不可用时继续工作？
   - 是否需要支持离线模式？

## 总结

**当前系统**:
- 不基于飞书多维表格
- 通过Excel文件导入数据
- 使用SQLite存储数据
- 使用React展示数据

**飞书新需求**:
- 需要与飞书集成
- 需要支持飞书工作流
- 需要支持飞书消息通知
- 需要定期数据同步

**建议方案**:
- 采用混合架构
- 飞书作为前端（工时填报和审批）
- 后端作为中间层（数据同步和业务逻辑）
- 网站作为展示层（统计和分析）
